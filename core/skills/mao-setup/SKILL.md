# MAO setup

A procedure, not a set of file formats. You are an agent running inside a harness; translate
the repo's tool-neutral content into that harness's native local config. Never rely on memory
of harness formats: they drift. Read the harness's current docs or `--help` first.

Modes: **install** (default), **uninstall** (see `manifest.md`), **dry-run**. Every mode
shows its full plan first and writes nothing, creates no directories and runs no installers
until the user approves.

**`<repo>`**: resolve this skill's file to its real path (follow symlinks; after install the
skill is a link) and walk up to the directory holding `core/AGENTS.md`; fail if there is
none. On re-runs prefer the `repo` value in the manifest if it still has `core/AGENTS.md`.
Never commit a path into the repo.

## Safety rules

- Show the complete plan (every path, link, file body, command) before any write; wait for
  explicit approval. Re-ask if the plan changes.
- Back up every file or link you replace to `~/.config/mao/backups/<timestamp>/`, keeping
  the original path structure. Never delete without a backup.
- Record every action in `~/.config/mao/installed.json` as you apply it (schema and action
  names in `manifest.md`).
- Idempotent: skip what is already correct (same link target, same content), but still
  record the current harness as a dependent of it. Update only what drifted, with a backup.
- Touch only files named in the plan. Never edit harness settings or credentials unless the
  plan lists the exact change.
- Never write to a path that resolves inside `<repo>`. Never commit or push in it.

## Procedure

### 1. Detect the harness and read its live docs

Identify the running harness (system context, CLI name, `--version`). Read its current
official docs or `--help` for:

1. Global (user-level) instructions file path, and whether it supports imports.
2. User skills directories it reads.
3. User subagent file format and directory, if any; whether it can preload skills.
4. Model choice: per spawn, per subagent file, or inherit-only; a per-file effort field.
5. Per-subagent tool restrictions and turn caps.
6. A way to list available models.
7. Which other harnesses' directories it also reads (for example `~/.claude/agents`,
   `~/.claude/skills`, `~/.agents/skills`).

Compare with `docs/harness-comparison.md` and trust live docs where they differ. If a fact
cannot be established, say so in the plan and skip that item rather than guess.

### 2. Plan the links

One list of actions, each with a type, target path and source.

**Global instructions.** The harness's global instructions file must be a REAL local file,
never a symlink into `<repo>`. Two cases:
- (a) The harness supports imports (Claude Code `@path`; check others live): write a stub
  with the import line `@<repo>/core/AGENTS.md` (absolute path; imports resolve relative to
  the importing file), then the Local section below.
- (b) No imports: generate a real file with the full `core/AGENTS.md` content, headed
  "Generated by mao-setup from <repo> @ <git short sha>; edit core/AGENTS.md and re-run
  mao-setup to refresh.", then the Local section. Record the file's sha256 and the source
  sha in the manifest. On re-run: core changed, offer refresh; local file hand-edited
  (sha256 differs), flag it and keep it by default.
- No global file (settings UI only): do not invent one; tell the user to paste or point it.
- If a file exists, compare it with `core/AGENTS.md` first. If it is a predecessor or has
  conflicting rules (routing to different agent names, model names), list the conflicts and
  recommend replace with backup. Offer append only for non-conflicting user content.
- **Local section** (`## Local (generated by mao-setup)`): `MAO skills: <repo>/core/skills`
  and a tier map chosen from live docs or the harness's model list, e.g.
  `Tiers here: fast=<model>, standard=<model>, deep=<model> (+ high effort)`. Local only,
  never committed; re-runs refresh it. Inherit-only harness: write "no per-spawn model
  choice; inherit" instead.

**Skills.** Each directory under `<repo>/core/skills/` is a skill, except
`second-brain-interface` (step 3). Symlink each into `~/.agents/skills/<name>` (always), and
into the harness's own user skills dir only if the harness does not read `~/.agents/skills`
(e.g. Claude Code `~/.claude/skills`, Cline `~/.cline/skills`, Kiro `~/.kiro/skills`).

**Role subagents.** If the harness has user subagent files, plan one thin file per role
(scout, mechanical, implementer, hard-implementer, reviewer, verifier, documenter) named
`mao-<role>`, containing:
- `description`: only the role sentences of the skill's description (drop the "Charter for
  ... do not load it" clause);
- tool limits from the skill's `Access:` line:

  | Access | Native limit |
  |---|---|
  | read-only | read/search only; no edit, no shell |
  | read+shell | read/search plus shell; edit tools denied |
  | edit | read/search plus edit; no shell |
  | edit+shell | read/search, edit, shell |

  Web access: scout yes; other roles none unless a harness default applies. If the harness
  only has coarse limits, pick the closest limit that still lets the role do its job (never
  make the documenter read-only) and add a prompt-level note for the remainder;
- model by the skill's `Tier:` line: per-spawn harness: `inherit`; per-file harness: a model
  per tier from the model list, or ask the user; inherit-only harness: tiers collapse, say
  so in the plan. Where there is a per-file effort field: fast=low, standard=medium,
  deep=high;
- a turn cap from the skill's turn-cap line where the harness has one;
- body: "Read `<repo>/core/skills/mao-<role>/SKILL.md` first and follow it as your charter."
  (read access exists at every level). Where the harness can preload skills (Claude Code
  `skills:` frontmatter), also preload `mao-<role>`; verify the field live.

No user subagent files: skip; `core/AGENTS.md` covers the generic-subagent fallback.

**Other harnesses' directories.** Using fact 7, make the native file win. Flag duplicates or
format mismatches (e.g. a Claude-format `mao-reviewer` that Cursor would also pick up) and
plan around them, asking the user if unclear.

### 3. Dependencies (ask y/N for each, separately)

All optional. "Present" means present in the target directory the plan would link into. If a
present copy differs from upstream (a stale `verify`, say), offer to replace it with a link
after backup. Show the exact command and source before asking.

| Dependency | Source | How |
|---|---|---|
| OpenSpec CLI | https://github.com/Fission-AI/OpenSpec | `npm i -g @fission-ai/openspec` |
| `verify` skill | https://github.com/Gamebreack/agent-verification (`.agents/skills/verify`) | link the skill dir |
| `megaplan` skill | https://github.com/Gamebreack/megaplan (`skills/megaplan`) | link the skill dir |
| `grilling`, `grill-me` | https://github.com/mattpocock/skills | `npx skills add mattpocock/skills` |
| Plugins `ui-ux-pro-max` (marketplace `ui-ux-pro-max-skill`), `pyright-lsp` (`claude-plugins-official`) | Claude Code only | its plugin commands; verify names live |

`verify`/`megaplan`: reuse an existing local checkout (ask for its path or search the usual
project directory); else clone to `~/.local/share/mao/vendor/<repo-name>`. Link as in step 2.
`npx skills add`: read its live `--help` for global and skill-selection flags; install only
`grilling` and `grill-me`, globally, and record what it changed for uninstall.
`second-brain-interface`: only on explicit request; needs a Second Brain MCP server MAO does
not ship. Link it like any skill.

### 4. Show, approve, apply, record

1. Print the full plan: per action its type (`link`, `write`, `edit`, `run`, `clone`,
   `retire`), path, and for writes the full body or diff.
2. Ask for explicit approval. In dry-run, stop here.
3. Apply: backups, then writes, then dependencies. Append each action to the manifest
   immediately.
4. Verify with evidence: list skills and subagents as the harness sees them, confirm links
   resolve, then spawn one role (the reviewer) and confirm it follows the charter's report
   format and cannot edit. Report mismatches; never claim success without this.

### 5. Retire superseded items

Candidates are only what the old MAO installer wrote, in Claude Code: 
`~/.claude/agents/{explorer,worker,mechanical-worker,hard-worker,reviewer,verifier,manager}.md`,
`~/.claude/hooks/manager-boundary.sh`, and the `settings.json` hook entry whose command
contains `manager-boundary.sh` (a separate candidate from the script). Never touch other
harnesses' directories: in Codex, `worker` and `explorer` are built-in override names, so any
such file is the user's.

Compare each file with the last pre-change version in `<repo>`: if `agents/` exists at HEAD
use `git -C <repo> show HEAD:agents/<name>.md`; otherwise find the removal commit
(`git log -1 --format=%H -- agents/`) and use its parent. Same for
`hooks/manager-boundary.sh`. If a file differs or cannot be compared, keep it by default.
For the settings entry, remove only that entry and leave everything else byte-for-byte.
Each retirement needs approval and a backup, is recorded as `retire`, and is not restored by
uninstall unless the user explicitly opts in.
